# Full Project Audit — 2026-08-10

> Purpose. Comprehensive prioritized audit of the Maith repo, ordered highest -> lowest
> impact, so fixes can be applied incrementally and deliberately with testing at each step.
> Each item lists: the problem, evidence, the affected code, and the recommended fix.
>
> Scope. Lean code (Maith/, Tests/), Python ML pipeline (python/, Scripts/),
> datasets, runs, git hygiene, and the relationship between trained models and current data.

## How to read this

- Impact = what breaks if unfixed (invalid results > broken tests > data gaps > cleanup).
- Effort = S (single file, <1h) / M (multiple files, half-day) / L (re-run training, hours/days).
- Each fix should be applied in isolation, followed by the listed test to confirm it is removed,
  then committed. Do not batch unrelated fixes -- incremental + tested is the goal.

## P0 -- CRITICAL: invalidates experiment results

### P0-1. Trained models do not match the current (rebuilt) datasets

Impact: ANY evaluation or retrieval run on variants A and B_small against the working-tree
datasets is invalid. The models saw different training data than what is now on disk.
Effort: L (requires retraining A and B_small on the clean 3375/376 split).

Evidence:

| Variant | model results.json train/eval | working-tree dataset | match? |
|---|---|---|---|
| A (variant_A_v1_4_0) | 3491 / 388 | 3375 / 376 | NO |
| B_small (variant_B_small) | 3491 / 388 | 3375 / 376 | NO |
| B (variant_B_phase6) | 3375 / 376 | 3375 / 376 | YES |
| C (variant_C_v2) | 3375 / 376 | 3375 / 376 | YES |
| flat (variant_flat) | 3375 / 376 | 3375 / 376 | YES |

The committed (HEAD) datasets are the old leaky split (3491/388, 13 overlaps; flat 3627/402).
The working-tree datasets were rebuilt clean (3375/376, overlap=0; flat now aligned to 3375/376).
build_dataset.py gained an uncommitted dedup step that removes duplicate example_ids before
splitting -- this is what shrank the counts. check_invariants.py passes on the working tree
(50/50) precisely because it reads the rebuilt datasets, but the A and B_small checkpoints
were trained on the pre-dedup data.

Why this is critical: the frozen probing representations (runs/probing/representations_A.pt,
shape [4029, 896]) were extracted from the full 4029-example corpus, not the 3375-train split --
so the probing task labels and the model that produced those representations are also
inconsistent with the current split. Any new probing or retrieval numbers computed from the
existing representations_A.pt cannot be compared to numbers from a future A retrain.

Fix:
1. Commit the rebuilt datasets (3375/376, clean) and the build_dataset.py dedup change so the
   repo has a single canonical split.
2. Retrain A and B_small on the clean split (keep variant_A_v1_4_0 as variant_A_v1_4_0_leaky
   for archival until the new run is verified).
3. Re-extract probing representations from the retrained A.
4. Test: python3 python/check_invariants.py (must stay 50/50) AND a new invariant that
   asserts every runs/*/results.json train_examples matches wc -l datasets/train_<v>.jsonl.

Supersedes KNOWN_ISSUES #1 (leakage) and #2 (flat split) -- both are fixed in the working
tree but the trained models lag, so the comparison is still invalid until A/B_small are retrained.

### P0-3. extract_representations.py feeds IR tokens to all variants

Impact: H6 retrieval embeddings for B, C, B_small are invalid -- those models were trained
on leanExpr/AST text, not IR tokens, so feeding IR tokens produces out-of-distribution
embeddings. KNOWN_ISSUES #4.
Effort: S (replace with the uncommitted extract_retrieval_embeddings.py) + L (re-extract).

Evidence: python/extract_representations.py in extract_representations_for_variant:
    tokens = ex.get("tokens", [])          # always the IR tokens from the corpus
    input_str = " ".join(tokens)
    encoded = tokenizer(input_str, ...)
This runs for every variant including B/C/B_small, which is wrong for them. The uncommitted
python/extract_retrieval_embeddings.py already fixes this by reading per-variant
input_ids from datasets/{train,eval}_{variant}.jsonl.

Fix:
1. Commit python/extract_retrieval_embeddings.py (currently untracked, not gitignored).
2. Either fix extract_representations.py to dispatch per-variant inputs (matching the new
   script) or deprecate it with a clear error that points at extract_retrieval_embeddings.py.
   Keep ONE extraction entry point to avoid the bug recurring.
3. Re-extract probing representations for every variant using the corrected, per-variant inputs.
4. Test: a new unit test asserting the extractor reads input_ids from the matching
   variant dataset, not ex["tokens"].

### P1-3. Injectivity test "Non-commutative operations do not collapse" fails

Impact: a real injectivity assertion is failing. Either the encoder is lossy in a way that
breaks injectivity (a correctness bug), or the test asserts behavior the v1.4.0 encoder
deliberately does not provide (a stale test). Must be resolved -- leaving a known-failing test
normalizes failure.
Effort: S (decision + one-file edit).

Evidence: Tests/InjectivityTests.lean:60 asserts sub(a,b) != sub(b,a) after
encode->normalize. But Maith/Encoder.lean encodeOperationWith emits:
    [ "O", arityToken o.inputs.length, outputToken bvarMap o.output, toString o.op ]
The inputs list is NOT encoded at all -- only its length (IN_N). So sub(a,b) and
sub(b,a) produce identical tokens. Tests/DecoderTests.lean:55-56 explicitly acknowledges
this: "v1.4.0 round-trip is structural (IN_N/OUT_N is lossy for input IDs)."

Fix decision (pick one):
- (a) If lossy inputs are intentional for v1.4.0 (the design comment says so), change the test
  to assert what the encoder actually guarantees: e.g. two ops with different arity or
  different op produce distinct tokens, and remove the operand-order claim with a comment
  explaining the v1.4.0 lossy design.
- (b) If operand identity matters for downstream probing/retrieval, restore input encoding
  (emit each input resolved token after the op) -- this is a larger change and changes the
  token format, so it implies retraining. Do NOT do this without retraining everything.
Recommendation: (a) is consistent with the documented design and avoids a retrain. Update
the test + add a comment pointing at the DecoderTests note.
Test: lake exe tests Injectivity suite -> 10/10 (or the renamed suite passes).

### P2-1. Epoch confound: variant_C_v2 trained for 3 epochs, all others 2

Impact: any A-vs-C or B-vs-C comparison conflates tokenizer choice with training budget.
Effort: S (verify) -> L (retrain C at 2 epochs if you want strict comparability).

Evidence: runs/variant_C_v2/results.json -> "epochs": 3; variant_C_phase6,
variant_A_v1_4_0, variant_B_small, variant_B_phase6, variant_B_v2_2ep -> "epochs": 2.
The primer noted a B/C 3-epoch confound (v1); the data now shows only C_v2 is the outlier.

Fix:
1. Decide which C checkpoint is canonical for the 2x3 comparison. If variant_C_phase6
   (epochs=2) is the right comparator, document that and stop citing variant_C_v2 numbers in
   A-vs-C comparisons.
2. If strict 2-epoch parity is required, retrain C at 2 epochs (a variant_C_v2_2ep mirror of
   variant_B_v2_2ep).
3. Add an invariant: check_invariants.py comparison-validity check should flag any pair being
   compared whose epochs differ.
4. This decision must be made BEFORE the P0-1 retrain (work-order step 8) so that if C needs
   a 2-epoch retrain, it runs in the same batch as A and B_small rather than as a separate
   training pass later.

1. Add learning_rate, batch_size (effective = BATCH_SIZE * GRAD_ACCUM), max_seq_len to
   the results dict in train.py.
2. Backfill existing runs/*/results.json where the true values are known from git history
   (B/C at 5e-5) -- add an actual_learning_rate field with a note it was backfilled.
3. Test: extend test_variant_config.py to assert the four new keys exist in a freshly
   written results.json.

## Recommended order of work

The principle: remove blocking test failures first so you have a green baseline, THEN fix
data/correctness with retraining, THEN hygiene. This lets each step be verified before the next.

1. P1-1 (serializer /tmp crash) -- makes lake exe tests runnable end-to-end.
2. P1-3 (injectivity test) -- reconcile test with documented lossy design.
3. P0-2 (regenerate module-mode corpus) -- unblocks P1-2.
4. P1-2 (regenerate GOLDEN for v1.4.0) -- restores the golden guard.
5. P2-3 + P2-4 (commit + clean retrieval scripts) -- repo has a single, reproducible H6 path.
6. P2-2 (record LR/batch in results.json + backfill) -- comparability for the retrain ahead.
7. P0-3 (switch to per-variant extraction) -- correct embeddings before re-extracting.
8. P2-1 (decide C checkpoint / optional C 2-epoch retrain) -- decide BEFORE the retrain so
   that if C needs a 2-epoch retrain, it can be batched into the same training run as A and
   B_small rather than done as a separate pass later.
9. P0-1 (commit clean split, retrain A + B_small [+ C if step 8 decided], re-extract reps) --
   the big one; do last so everything it depends on is already correct.
10. P3-1 ... P3-4 (cleanup + CI) -- once the test gate is green, wire it so regressions
    cannot silently return.
